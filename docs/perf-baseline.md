# DeFiScope AI — Catalog performance baseline (Phase 0)

Generated by `scripts/perf_bench.py`. Latencies in ms. Each workload runs `iters` times against the real `app.services.catalog` read functions (page + `COUNT(*)` included).

## Findings & decisions (drive Phases 1–2)

Production catalog today is ~8.9k protocols. At that size **every** workload is under 15 ms p95 — indexes are not the bottleneck, confirming the plan's premise. The numbers that matter appear only as we approach the 50k–100k headroom the plan asks for:

| path | 5k p95 | 50k p95 | 100k p95 | verdict |
|---|---|---|---|---|
| default tvl page | 2 | 12 | 37 | sort uses a **temp B-tree** (the portable `tv IS NULL` nulls-last key defeats the `tvl` index) — worth an index-ordered read at 100k |
| `search q=aave` | 7 | 64 | **130 ⚠** | `%term%` full-scan; needs a trigram/GIN (Postgres) or FTS (SQLite) accelerator by ~100k |
| chain filter | 4 | 32 | 77 | uses indexes but the `IN (subquery)` + bloom-filter grows; candidate for a join rewrite |
| **deep page (offset)** | 14 | **481 ⚠** | **929 ⚠** | **worst path, O(offset)** — no index fixes this; needs keyset pagination or a bounded page depth |
| count (unfiltered) | 0.4 | 2.7 | 8.6 | cheap — covered by the PK covering index; **lower priority than the plan assumed** |
| facets | 0.3 | 0.2 | 0.3 | trivially cheap; caching optional |

**Refined priorities (measured, not assumed):**
1. **Pagination depth** is the dominant tail-latency risk, not the index set — an OFFSET scan cannot be indexed away. Address with keyset (cursor) pagination or a max-page cap so a caller can't jump to page 3,900.
2. **Search** is the second: a Postgres `pg_trgm` GIN (Phase 2) closes it; SQLite stays fine to ~50k, FTS5 deferred until proven.
3. **Sort ordering** (temp B-tree) → Postgres `NULLS LAST` + `(tvl DESC NULLS LAST, slug)` index; revisit SQLite expression index only if 100k latency matters locally.
4. **Count/facet caching** is *lower* value than the plan guessed (unfiltered count rides the PK covering index at 5–9 ms). Still apply (cheap, zero-risk), but it is not the headline win.

Caveats: SQLite single-file, warm page cache, `iters=200`. Postgres plans require a scratch DB via `--db ... --confirm-pg`. Absolute ms differ on real hardware; the *relative* scan/sort/offset findings are what the plan acts on.
